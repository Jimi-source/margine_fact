# Проект: margine-fact

Веб-сервис для расчёта маржинальности товаров на OZON. Пользователь загружает Excel/CSV файлы из личного кабинета OZON и получает расчёт маржи по каждому SKU.

## Стек и инфраструктура

- **Backend**: Node.js / Express (`index.js`)
- **Frontend**: HTML/CSS/JS (`index.html`, `app*.js`, `styles.css`)
- **БД**: PostgreSQL на VPS (31.130.130.129)
- **Деплой**: VPS через PM2 (`marginefact-api`), frontend на Vercel (`https://margine-fact.vercel.app`)
- **CI/CD**: GitHub Actions → git pull + pm2 restart на VPS при каждом push в main
- **Auth**: JWT (bcryptjs + jsonwebtoken)
- **Email**: Resend
- **Кредиты**: платная система, пакеты 1/3/5/10 кредитов

### cashflow entry (JSONB-структура)

```js
{
  marginBeforeTax: 0.4281,
  summary: { totalAds, totalAccrual, totalCost, revenueBeforeTax, marginBeforeTax,
              totalCancelSum, summaryMarginWithoutCancel, otherServicesTotal,
              tax5, tax9, netWithTax5, netWithTax9, marginAfterTax5, marginAfterTax9,
              realizTotal, totalByGroup, totalQty },
  rows: [...],               // per-SKU строки (сохраняются с v.aaee268)
  accrualGroups: [...],
  stencilAdsByArticle: {},   // стенсил-часть рекламы по артикулу
  pvpAdsByArticle: {},       // ПВП-часть рекламы по артикулу
  stencilOrderCountsInPeriod: {}, // "article__date" → {count, skuName}
  locked: false,             // если true — период не пересчитывается автоматически
  updatedAt: "ISO"
}
```

**Про `rows`:** сохранение построчных данных добавили недавно, поэтому у старых периодов `rows` пустой — доступны только агрегированные `summary`. На 25.08.2026: разбивка по SKU есть с недели 06.07.2026 (7 недель из 34). Если нужна история по SKU глубже — её просто нет в БД.

**Про `row.accrualByGroup`:** в сохранённых строках это поле ЕСТЬ (`{"Продажи": ..., "Возвраты": ..., "Вознаграждение Ozon": ..., ...}`). Не полагаться на предположение, что его нет.

**Проверка целостности:** `summary.totalAds` и `summary.totalAccrual` должны совпадать с суммой по `rows` (проверено на всех неделях с разбивкой — сходится до копейки). При этом `summary.totalAds` НЕ равен сумме `stencilAdsByArticle` + `pvpAdsByArticle`: эти карты покрывают только артикулы, у которых был соответствующий вид рекламы. Не принимать это расхождение за баг.

## Входные файлы от пользователя

Пользователь загружает 3-5 файлов из OZON:

| Файл | Содержимое | Ключевые колонки |
|------|-----------|-----------------|
| **Заказы** | все заказы за период | Артикул, Статус, Номер заказа/отправления, Количество, Delivery date |
| **Начисления** | финансовые операции | Артикул, Тип начисления, Сумма итого, Дата принятия заказа, Название товара, ID начисления |
| **Трафарет** | расходы на рекламу (Stencil/CPM) | День, Название товара, Расход ₽ с НДС |
| **ПВП** | реклама за клики | Номер заказа, Продвижение ₽ |
| **Себестоимость** | закупочная цена | Артикул, Себестоимость |

### Важно про файлы трафаретов

- Пользователь консолидирует данные по ВСЕМ рекламным кампаниям в ОДИН сводный файл перед загрузкой (несколько кампаний работают параллельно)
- Файл трафаретов покрывает ШИРОКИЙ диапазон дат — как правило 3-6 недель назад от текущей даты
- Имя файла: `{campaign_id}_{start}-{end}.xlsx` — но campaign_id несущественен, это просто имя

## Алгоритм расчёта маржи (`calculateReport` в index.js)

### 1. Статусы заказов

Только строки начислений со статусом "Доставлен" (statusScore === 1) идут в расчёт выручки. Статус матчится через ID начисления → Номер заказа/отправления из файла заказов.

### 2. Начисления (accruals)

Суммируются по артикулу. Группы: Продажи, Возвраты, Услуги доставки, Вознаграждение Ozon, Продвижение и реклама, Другие услуги/штрафы. "Другие услуги" без артикула идут в `otherServicesTotal`.

### 3. ПВП (реклама за клики)

`pvpSumByOrderArticle`: суммируется по (Номер заказа, Артикул) из файла ПВП. Делится на кол-во строк с этим заказом → `promotionPerRow`. Добавляется к `adsByArticle[article]`.

### 4. Трафарет (Stencil/CPM) — самая сложная логика

#### Прямой расчёт (при первом расчёте периода)

```
stencilKey = date__skuName  (из начисления: дата заказа + название товара)
stencilSum = stencilSumByKey[stencilKey]  (из файла трафарета за эту дату)
count = кол-во строк начислений с (article, date)
stencilValue = stencilSum / count  (на одну строку начисления)
```

#### Проблема: "хвост" заказов

Начисления за период 29.06-05.07 содержат **заказы с датами 3-4 недели назад** (18-28 июня и раньше), потому что товар заказали в июне, а доставили в июле. В итоге расходы по трафарету за июньские даты попадают И в июньские периоды (при их расчёте) И в июльские (снова). **Это приводит к двойному счёту.**

#### Решение: Реестр трафаретов

**`stencil_spend_registry`** (`user_id, date, sku_name → total_spend`):
- При каждом расчёте файл трафарета записывается в реестр (UPSERT: последнее значение побеждает)
- Хранит суммарный расход по всем кампаниям за каждый день по каждому товару

**`stencil_order_registry`** (`user_id, period_start, period_end, date, article → total_count`):
- Хранит: сколько строк начислений с `(article, date_of_order)` попало в данный расчётный период
- UPSERT идемпотентный по (user_id, period_start, period_end, date, article)

#### Формула распределения

```
stencil_for_period[article][date] =
    period_count × (total_spend / total_orders)
где:
  period_count = stencil_order_registry[period][date][article]  // кол-во в ЭТОМ периоде
  total_spend  = stencil_spend_registry[date][sku_name]          // общий расход из реестра
  total_orders = SUM(stencil_order_registry[*][date][article])   // SUM по ВСЕМ периодам
```

**Смысл**: расход за дату X делится пропорционально между всеми периодами, в которых есть начисления с датой заказа X. Это устраняет двойной счёт.

#### Автопересчёт прошлых периодов

При каждом новом расчёте сервер:
1. Обновляет оба реестра
2. Загружает все cashflow-периоды пользователя за текущий и прошлый год
3. Для каждого незафиксированного периода с `stencilOrderCountsInPeriod` вызывает `recalcEntryStencil()`
4. Сохраняет изменённые периоды в БД

`recalcEntryStencil` (index.js ~1043):
- Берёт `stencilOrderCountsInPeriod` из сохранённого cashflow-entry
- Считает новые стенсил-значения по актуальному реестру
- Пересчитывает summary: `totalAds`, `revenueBeforeTax`, `marginBeforeTax`, `summaryMarginWithoutCancel`
- Пересчитывает per-SKU строки `rows`: для каждой строки `newAds = newStencil + pvp` (если `pvpAdsByArticle` сохранён), далее `revenue`, `margin`, `marginWithoutCancel`
- Возвращает `null` только если И `|deltaStencil| < 0.01`, И ни одна строка не изменилась (`rowsChanged === false`)

**Важно про порядок проверок.** Проверка `deltaStencil` стоит ПОСЛЕ вычисления `updatedRows`, а не до. Если вернуть `null` раньше по дельте summary, строки никогда не догонят реестр: `stencilAdsByArticle` уже обновлён прошлыми пересчётами (дельта = 0), а `rows` остались с исходного расчёта. Именно так выглядел баг — см. раздел про баг №5 ниже.

#### Период стабилизируется через ~4 недели

После 4 недель хвост заказов иссякает. Тогда можно зафиксировать период (`locked: true`) и он больше не будет пересчитываться.

#### Файл трафаретов обязан покрывать широкий диапазон дат

Грузить только за прошедшую неделю НЕЛЬЗЯ. Причина в index.js:363 — реестр заказов заполняется только по строкам, для которых в **загруженном сейчас файле** есть расход:

```js
if (article && stencilSum > 0) {   // stencilSum — из файла, НЕ из реестра
  stencilOrderCountsInPeriod.set(periodKey, ...)
}
```

Реестр расходов (`stencil_spend_registry`) накапливается, старые даты не теряются. Но если файл не покрывает дату X, хвостовые заказы с датой X в этом периоде не попадут в `stencil_order_registry`, знаменатель `total_orders` окажется занижен, и расход за дату X перераспределится на прошлые периоды вместо текущего. Двойного счёта не будет (сумма сойдётся), но распределение съедет: новая неделя получит рекламу бесплатно, прошлые заберут её расход на себя.

Пример: дата 20.07, расход 1000 ₽, строки начислений — 30 в периоде 20.07-26.07, 15 в 27.07-02.08, 5 в 10.08-16.08.

| | total_orders | 20.07-26.07 | 27.07-02.08 | 10.08-16.08 |
|---|---|---|---|---|
| Полный файл | 50 | 600 | 300 | 100 |
| Только последняя неделя | 45 | 667 | 333 | 0 |

Возможное улучшение (НЕ реализовано): строить `stencilOrderCountsInPeriod` по реестру расходов, а не по загруженному файлу. Требует загрузки реестра ДО `calculateReport`.

## Структура frontend-расчёта (app-calc.js)

### state (app-globals.js)

```js
state = {
  lastRows: [],                    // текущие per-SKU строки
  lastSummary: {},                 // итоговый summary
  lastCalcRange: {start, end},
  forecastData: {deliveringByArticle, cancelRate},  // прогноз маржи
  lastStencilAdsByArticle: {},     // {article: {stencil, pvp}} из ответа сервера
  accrualGroups: [],
  cashflow: {year, granularity, periods, entries, selectedKey, taxRate, saveTimer}
}
```

### Per-SKU строки (row object)

```js
{
  article, skuName, qty, accrual, ads, costSum,
  margin, revenue, cancelSum,
  marginWithoutCancel, revenueWithoutCancel,
  otherPerArticle
}
```

### Прогноз маржи

- Берутся заказы в статусе "Доставляется" из файла заказов
- `cancelRate = cancelled / (delivered + cancelled)` по историческим данным из того же файла
- Для каждого "Доставляется"-заказа вычисляется ожидаемая маржа: средние начисления − реклама (с реестровой корректировкой) − себестоимость
- Реклама берётся из `lastStencilAdsByArticle` (registry-corrected), а не из `row.ads`
- Результат: колонка "Прогноз маржи" в таблице и сводная цифра в блоке результатов

### Сохранение cashflow-периода

При нажатии "Сохранить":
1. Строки корректируются: для каждого артикула `ads` заменяется на `stencil + pvp` из реестровых данных
2. Сохраняется: `{marginBeforeTax, summary, rows (corrected), accrualGroups, stencilOrderCountsInPeriod, stencilAdsByArticle, pvpAdsByArticle}`
3. Отправляется в `/cashflow` (POST)

### Drill-down в кэшфлоу

При открытии периода из кэшфлоу (если есть сохранённые `rows`):
- Восстанавливает `state.lastRows`, отсортированный по `row.accrual` DESC, и `state.accrualGroups`
- `state.forecastData = null`, `state.lastStencilAdsByArticle = {}` (нет актуального реестра)
- Рендерит таблицу с per-SKU данными без прогноза маржи — передавать в `renderTable()` именно `state.lastRows`, а не `entry.rows` (иначе порядок строк будет несортированным, см. баг №7)

## Известные тонкости и баги (исправленные)

### 1. Shadowing-баг (исправлен в ~fa87345)

В stencil try/catch были `const spendRegistry = {}` и `const orderRegistry = {}` внутри блока, которые затеняли внешние `let`. Реестр всегда был пустым при пересчёте текущего периода. Исправлено: убраны `const`, присваивание идёт во внешние переменные.

### 2. Файл трафаретов покрывает широкий диапазон

Файл за 13.07-19.07 может покрывать даты с 29.06. При записи в реестр он **перезаписывает** данные за 29.06-05.07. Это правильно: пользователь консолидирует все кампании в один файл, поэтому последнее значение — актуальное.

### 3. Автопересчёт меняет цифры прошлых периодов

Это намеренное поведение. После загрузки трафаретов за новую неделю, прошлые периоды пересчитываются с учётом новых данных о том, сколько заказов тех дат доставилось позже. Пользователь должен это понимать.

### 4. Период 29.06-05.07 имел заниженный трафарет

При первом расчёте использовался неполный набор рекламных файлов. После загрузки полного сводного файла трафаретов (кампании 30672200, 29647905, 30332204, 29861754) при следующем расчёте автопересчёт скорректировал значения.

### 5. `recalcEntryStencil` не обновлял per-SKU строки (исправлен, commits 1e49bc4 → e393729)

Автопересчёт правил `summary` и `stencilAdsByArticle`, но не `rows`. В drill-down по периоду показывалась устаревшая реклама и маржа по каждому SKU, хотя итог по периоду был верный.

Первая попытка (1e49bc4 — добавить `rows: updatedRows` в return) не помогла: функция выходила раньше по `if (Math.abs(deltaStencil) < 0.01) return null`. К тому моменту `stencilAdsByArticle` уже был обновлён предыдущими прогонами, дельта была нулевой, а `rows` так и оставались стухшими. Исправлено в e393729: проверка дельты перенесена ПОСЛЕ вычисления `updatedRows`, добавлен флаг `rowsChanged`.

**Диагностический приём:** если `updatedAt` у периода меняется, а данные нет — функция вызывается, но возвращает `null` или обновляет не то поле. Смотреть на порядок ранних `return`.

### 6. Пропадала вкладка cashflow (исправлен, commit ba1705a)

В `loadUserCredits` (app-auth.js) блок `catch` сбрасывал `state.userRole = null` при любой сетевой ошибке. Далее `updateOwnerUI()` видел, что роль не `owner`, и прятал вкладку cashflow. Помогал только повторный вход. Исправлено: `userRole` больше не сбрасывается в `catch` — вкладки остаются видимыми при обрыве сети.

### 7. Сортировка строк результата не работала (исправлен, commits 4d861b6 → 9b01120)

Строки результата должны идти по убыванию продаж. Две ошибки подряд:
1. Сортировали по `getSalesValue(row.accrualByGroup)` — но правильнее и надёжнее по `row.accrual`, оно есть всегда
2. В drill-down сортировали `state.lastRows`, а в `renderTable()` передавали несортированный `entry.rows`

Итог: сортировка по `row.accrual` DESC в двух местах — [app-calc.js:41](../../app-calc.js) при новом расчёте и [app-cashflow.js:356](../../app-cashflow.js) при открытии периода из кэшфлоу, там же `renderTable(state.lastRows)`.

Замечание: пользователь просил сортировку «по полю Продажи», а фактически сортируется по `accrual` (Начисления). На практике порядок почти совпадает, но это не буквально то, что просили — если всплывёт, менять на `getSalesValue(row.accrualByGroup)`.

## Работа с БД на VPS (частые грабли)

Подключение к PostgreSQL из скрипта на VPS:

```js
// В .env НЕТ DATABASE_URL — есть отдельные переменные
const env = /* распарсить /var/www/marginefact-api/.env */;
const pool = new Pool({
  host: env.DB_HOST, port: env.DB_PORT, database: env.DB_NAME,
  user: env.DB_USER, password: env.DB_PASS
});
```

- **`DATABASE_URL` не существует** — только `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASS`. Попытка `new Pool({ connectionString: process.env.DATABASE_URL })` даёт `SASL: client password must be a string`.
- **Скрипт должен лежать внутри `/var/www/marginefact-api/`** — Node ищет `node_modules` относительно файла, а не текущего каталога. Из `/tmp/script.js` будет `Cannot find module 'pg'`, даже если сделать `cd` в каталог проекта.
- **`user_id` — это email, не число.** Значения: `prudnikovegor@mail.ru` (владелец, основные данные) и `anngorodetskaya@mail.ru`.
- **Себестоимость лежит в `user_sebes.items`** (JSONB), таблица `sebes` пустая.
- **Доступ к VPS** — реквизиты в `vps_credentials.rtf` в корне проекта (файл НЕ в git). Пароли в этот скилл не писать: он коммитится в репозиторий.
- Временные скрипты после работы удалять с VPS.

## Рабочий процесс пользователя

1. Открыть сайт → выбрать период (неделя)
2. Загрузить файлы: заказы + начисления + трафарет (сводный по всем кампаниям) + ПВП (опционально)
3. Нажать "Рассчитать" → получить таблицу по SKU с маржой, рекламой, прогнозом
4. Нажать "Сохранить в кэшфлоу" → период сохраняется, прошлые периоды автоматически пересчитываются
5. Через ~4 недели зафиксировать период (locked: true) — он больше не будет пересчитываться

## Важно про несколько кампаний трафаретов

Пользователь может вести несколько рекламных кампаний одновременно. Кампании не пересекаются по (дата, SKU) — у каждой свои товары. Поэтому UPSERT в реестр не затирает данные других кампаний — каждая пишет свои уникальные строки.

Перед загрузкой пользователь объединяет файлы всех кампаний в один сводный файл. Это гарантирует что реестр всегда содержит полные суммарные данные.

**Названия файлов могут не соответствовать содержимому.** Встречалось: файл «ПВП.xlsx» на самом деле содержал трафарет («Кампания по продвижению товаров», колонки День / Показы / Расход с НДС), а файл «Оплата за закз.xlsx» — настоящий ПВП («Оплата за заказ», колонки Номер заказа / Ставка / Расход). Определять тип по заголовкам внутри файла, а не по имени.

## Telegram-бот удалён с VPS (03.08.2026)

На VPS был второй PM2-процесс `claude-bot` (`/var/www/claude_bot.js`), который правил файлы прямо на сервере и пытался делать `git push`. Push падал: `Password authentication is not supported for Git operations` — GitHub отключил пароли, нужен PAT или SSH-ключ.

Процесс остановлен, удалён из PM2 (`pm2 delete claude-bot && pm2 save`), файл удалён. В PM2 остался только `marginefact-api`.

**Решение по совместной работе:** пользователь согласился менять код только через Claude Code, а бота для правок кода не использовать. Причина — конфликт источников истины: бот писал на VPS, локальный репозиторий отставал, при деплое изменения затирались. Если бота будут возвращать, правильная схема — он коммитит через GitHub API, а VPS только принимает деплой и никогда не отправляет.

## Выгрузка данных для внешнего анализа

`marginefact_export.json` в корне проекта — самодокументированная выгрузка всех данных пользователя для скармливания ИИ (прогнозная юнит-экономика). Не в git (untracked, правил в `.gitignore` нет).

Структура: `_описание`, `_как_считается_маржа`, `_глоссарий`, `_предупреждения`, `меta_экспорта.покрытие`, `справочник_товаров`, `себестоимость_текущая`, `недели[]`, `месяцы[]`, `расход_на_трафареты_по_дням[]`. Ключи на русском, суммы округлены до копеек, доли маржи — доли единицы (0.4035 = 40.35%).

Что учитывать при обновлении:
- Названия товаров брать из `stencil_order_registry` (там есть и `article`, и `sku_name`) и складывать в справочник ОДИН раз, а не в каждую строку — иначе файл раздувается вдвое
- Внутри `недели[]` разбивка по SKU есть только у последних недель — это отражать в `меta_экспорта.покрытие`
- Обязательно предупреждать модель, что последние 3-4 недели предварительные: их цифры меняются автопересчётом. Реальный пример: неделя 10.08-16.08 при первом расчёте показывала маржу 33.65% и рекламу 70 225 ₽, после загрузки трафаретов за 17.08-23.08 стало 49.70% и 44 853 ₽
